PHASE 3 — CONCURRENCY & AUDIT HARDENING
STATUS: COMPLETE
PRIORITY: HIGH / PRODUCTION SAFETY
------------------------------------------------------------

Goal:
Make multi-user, multi-PC operation safe.

Known issues (confirmed in the code, not just the roadmap):
  - `sendPackage` (Backend/submissions.ts) never checked whether an
    identical send was already under way or already complete before
    creating a new `submission_package` and dispatching email. Two
    near-simultaneous calls (two employees, or one double-click) could
    both pass the document-set fingerprint check and both reach
    `provider.send` for the same documents before either transaction's
    writes were visible to the other. The existing
    `where status = 'not_submitted'` guard on `submission.status`
    prevented a second CASE transition, but not a second DISPATCH — the
    email had already gone to the bank by the time that guard ran.
  - `regenerateRequirements` (Backend/requirements.ts) ran on every read
    of a case's requirements (`listCaseRequirements`, called from a GET),
    inserting/updating/retiring `document_requirement` rows with no
    audit event at all — and even its own UPDATE was unconditional,
    rewriting a row to the values it already had on every call.

Resolution:
  - Backend/submissions.ts: `sendPackage` and `retryPackage` now open
    their critical section with `pg_advisory_xact_lock(hashtextextended
    (submissionId, 0))` — transaction-scoped, released automatically on
    commit/rollback, keyed on the submission id so different submissions
    (including two submissions on the same case) never block each other.
    After the lock is held, `sendPackage` re-reads authoritative state
    and checks for an already-`sent` package whose document set
    (id@version) matches the one being sent; if one exists, it returns
    that package's result instead of creating a duplicate and calling
    the provider again. A different document set (a document added,
    replaced or removed) is a genuinely new batch and is not blocked —
    preserving the existing "a second send is a new package" behavior
    for a deliberate resend. A failed/partially-sent package is
    untouched by this check, so `retryPackage` continues to work
    exactly as before, now itself serialized by the same lock.
  - Backend/requirements.ts: `regenerateRequirements` now compares each
    row's would-be new values against what is already on file before
    writing, and only executes the UPDATE when something actually
    differs. Every insert, real update and retirement (mark
    `not_applicable`) is tallied; if the tally is non-zero, one batched
    `requirement.regenerated` event is recorded (Backend/events.ts,
    `recordSystemRequirementEvent`) in the SAME transaction as the
    mutations, as a `system`-actor event (nobody clicked "regenerate";
    the reconciliation is a side effect of reading the case, the same
    reasoning `case.stage_changed` already uses for the transition
    machine's own automatic moves). A reconciliation that changes
    nothing writes no event. The payload carries only counts and
    requirement ids — no names, no document type labels, no case-party
    linkage.
  - No database migration. `pg_advisory_xact_lock` needs no schema
    change; the audit event reuses the existing `event` table (its
    `entity_type` column is unconstrained text) and the existing
    `recordSystem*Event` pattern.
  - `listCaseRequirements` remains a GET that regenerates on read — this
    was deliberately NOT changed to a separate mutation endpoint. The
    existing architecture (Backend/cases.ts's stage-transition guard,
    the All Cases progress list) depends on regeneration running inline
    on every read, and BR-050 ("a state change and its event commit
    together, or the change does not happen") is satisfied by the fix
    above without moving where regeneration happens. Splitting read from
    write here would be the broad REST redesign this phase is explicitly
    scoped to avoid.

Scope:
  - Make submission idempotent / transactionally safe. DONE.
  - Prevent duplicate lender emails. DONE.
  - Handle concurrent submissions correctly. DONE.
  - Move mutating regeneration behavior behind the appropriate mutation
    path if required by the existing architecture. NOT REQUIRED — see
    resolution above; the existing inline-on-read architecture is kept.
  - Add the missing audit event. DONE.
  - Preserve existing append-only audit semantics. DONE — the `event`
    table's append-only trigger and payload discipline are untouched.

Exit criteria:
  - Concurrent submission cannot send duplicate packages. PROVEN —
    Backend/submissions.test.ts, "concurrency — sendPackage serialises
    on the submission (Phase 3)".
  - Repeated submission is safely handled. PROVEN — same suite, plus the
    pre-existing retry regression tests (unmodified, still passing).
  - Mutating operations are represented correctly in the API. Requirement
    regeneration's mutation is now audited; see above for why the GET
    shape itself was kept.
  - Required audit events exist. PROVEN — Backend/requirements.test.ts.
  - Concurrency tests pass. PROVEN — full integration suite: 159/159.

PHASE 4 — CASE COMPLETENESS

PRIORITY: HIGH / REQUIRED FOR BROADER REAL-WORLD CASES

Goal:
Represent the parties and assets that real loan cases actually contain.

Reconnaissance found the schema and the requirement engine ALREADY assumed
this milestone would happen and left the seams for it:

    referrer and borrower_firm roles, `is_primary`, `removed_at`/`removed_by`

    rewrite of the shared person/organisation record.
  - `case_property` (0004) already models the case-to-property link and its
    role (`collateral`/`purchase`/`both`), same soft-removal shape.
  - `document_requirement` (0005) already carries `waived_by`, `waived_at`
    and `reason`, with constraints requiring all three or none

    `document_requirement_waiver_is_reasoned`) — BR-035 was written into the

    and `case_property` rows into `PartyFacts`/`PropertyFacts`, and the rule

    party-scoped and property-scoped rules once per role that actually
    exists (0021's design: "absence is silence" falls out of the design
    rather than being enforced by a check).

The actual gap was narrow: NOTHING WROTE TO `case_party` or `case_property`
past case creation, and nothing wrote a waiver to `document_requirement`.
`Backend/cases.ts`'s own header said so explicitly ("Case parties beyond the
primary applicant, and case properties, go with [documents/requirements] —
they exist to feed the requirement engine, which has not moved").

Implementation:
  - `Backend/case-composition.ts` (new). `addCaseParty` /
    `updateCasePartyProfile` / `removeCaseParty` and `addCaseProperty` /
    `updateCaseProperty` / `removeCaseProperty`, plus `listCaseParties` /
    `listCaseProperties`. Attaching an EXISTING person/organisation/property
    needs only `case.update`; creating a genuinely new one inline
    additionally needs `person.create` / `organisation.create` /
    `property.create` — the same permission that already governs writing to
    those tables directly, checked inside this module. The primary
    applicant cannot be added or removed here (0004's own constraints
    assume exactly one, set once at case creation).
  - `Backend/documents.ts` gains `waiveRequirement`, next to
    `decideDocument` (every other `document_requirement` status
    transition). Requires `requirement.waive` and a non-empty reason;
    refuses to waive an already-verified or already-not_applicable row;
    waiving the same row twice is a no-op (no duplicate event). Triggers the
    same stage reconciliation an upload or verification does — a waiver can
    be the last outstanding requirement on a file.
  - `Backend/events.ts` gains `case.party_added` /
    `case.party_profile_updated` / `case.party_removed` /

  - `Backend/api-server.ts`: `/api/cases/:id/parties[/:partyId]`,

Goal:

Known gap (as found — confirmed true before this phase):
  - Sanction tracking was not implemented.
  - Rejection tracking was not implemented.
  - Disbursement tracking was not implemented.
  - The stage machine effectively dead-ended at Submitted.

What this phase actually was: the schema (`submission_status` enum, `offer`,
`submission_query`, `rejection_reason`, the BR-022/023/024/025 constraints
and the deferred `submission_sanction_has_offer` trigger), the permissions
(`submission.update_status`, `offer.read`/`record`/`accept`) and the domain
stage-derivation logic (`deriveSystemStagePath`, `sanctionHasOffer`,
`disbursementExists`) already existed, unused, since Stage 3D. This phase
wired them to the real backend and frontend — no new tables, no new
permissions, no new stage-derivation logic.

Scope (delivered):
  - Record lender sanction outcomes — `updateSubmissionStatus(..., "sanctioned")`,
    refused without an offer on file (BR-023, checked in the app for a clean
    error and enforced regardless by the deferred DB trigger).
  - Record rejection outcomes/reasons — `updateSubmissionStatus(..., "rejected")`,
    requires an active `rejection_reason` row (BR-024); never moves the case
    backwards (`deriveSystemStagePath` is one-directional).
  - Record disbursement — `updateSubmissionStatus(..., "disbursed")`, one
    disbursed submission per case (BR-022, DB unique index + app check).
  - The bank-query loop — `raiseQuery`/`answerQuery`, writing `submission_query`.
  - The offer workflow — `recordOffer` (revisable — a live submission may
    carry more than one offer row before acceptance) and `acceptOffer`, which
    withdraws every other live submission on the case (BR-025) inside one
    transaction, each withdrawal individually audited.
  - The case lifecycle advances automatically — `Backend/case-stage.ts`'s
    `advanceCaseStage` walks `deriveSystemStagePath`'s full multi-step path
    (e.g. `submitted -> sanctioned -> disbursed` in one visit), never a
    manual "Move stage -> Sanctioned/Disbursed" choice (those remain
    `actor: "system"` rows in the transition table, so `userSelectableStages`
    already excluded them — no frontend change was needed there).
  - Multi-bank independence — each `submission` row keeps its own status;
    one bank's rejection never touches another's live submission on the
    same case.
  - Audit trail — new event types (`submission.under_process` /
    `query_raised` / `query_answered` / `eligibility_received` /
    `sanctioned` / `rejected` / `withdrawn` / `disbursed`, `offer.recorded`,
    `offer.accepted`), all payload-disciplined (ids/counts only, matching
    every other event recorder in `Backend/events.ts`).
  - Concurrency — every outcome mutation takes `pg_advisory_xact_lock`
    on the case (`lockCaseForOutcomeMutation`), a second lock key alongside
    Phase 3's per-submission send lock; simple status writes are additionally
    guarded by an atomic `UPDATE ... WHERE status = $from`.
  - BanksTab.tsx gained the operational UI: status actions gated by current
    status and permission, offer recording/display/acceptance, a rejection-
    reason picker, and the bank-query raise/answer flow. CaseDetail's Move
    Stage UI was not changed — it already excluded system-actor stages.

Explicitly NOT delivered (deferred, as scoped):
  - Inbound bank-email ingestion (Gmail polling, AI classification, OCR).
    The submission_status/offer/query model this phase completed is exactly
    what a future ingestion pipeline would write into — nothing here
    precludes it, nothing here builds it.
  - New document types for sanction letter / rejection communication /

Database:
  ZERO migrations. Verified true — every table, column, constraint, index,

PHASE 6 — CASE INTAKE & DOCUMENT WORKFLOW: COMPLETE
============================================================

THE DEFECT. The requirement engine could tell salaried from self-employed
from migration 0021, and the rule pack has read that distinction properly
since 0026 — payslips and Form 16 on one side, ITR, Form 26AS, CA-certified
accounts and GST returns on the other. Nothing ever WROTE the fact.
`createCase` took an applicant, a product, an amount and a source, so
`party.employment_type` resolved to unknown on every real case, every
income-conditioned rule matched nothing, and the login desk received KYC plus
whatever the product code alone could justify. The engine was not wrong; it
was never told anything. The fix is overwhelmingly in the INTAKE, not in the
rules: no new rule was written for it.

WHAT CHANGED

1. NEW CASE captures the facts the engine needs, by progressive disclosure.
   Pick the loan type; only the questions that loan type can answer appear.
   WHICH questions appear comes from what the product DECLARES
   (employmentTypeIds, businessConstitutionIds, propertyRequirement,
   gstRequirement — ADR-032, migrations 0015/0016), never from a list of
   product codes in the browser: a product added in Master Data next year
   asks the right questions with no frontend change. Every question is
   optional — unanswered means "nobody has asked", which the rules already
   distinguish from "no", and all of it is correctable on the case afterwards.

2. MIGRATION 0035 (additive). `case_party.itr_filed` and
   `case_party.is_gst_registered` — two facts that had nowhere to live, both
   deliberately three-valued. `document_type.artifact_kind` — who PRODUCES a
   document (customer / bank_submission / internal).

3. CUSTOMER DOCUMENTS ONLY. Three rules asked for documents the customer does
   not produce: the bank login form, the NACH mandate (both the lender's, and
   non-existent until a lender is chosen) and Amaze's own application form.
   They were on every case, and live use answered them by waiving them —
   which spends a decision that is supposed to mean "this file goes to the
   bank with a known gap, and my name is on it" (BR-035). All three are now
   is_active = false with the reason on the row; nothing deleted, nothing
   rewritten, and existing requirements retire to not_applicable through the
   ordinary regeneration path (BR-034).

4. ITR CONDITIONALITY. `party.itr_filed not_equals "false"` — fires on YES
   and on UNKNOWN, stands down only on an explicit NO. Deliberately not
   `is_true`, which would have asked nothing until somebody ticked a box: the
   exact bug the 9.1 audit found on the GST rules.

5. SUBJECTS ARE STRUCTURAL. The API returns `requirement.subject`
   ({kind, role, name}) resolved from `required_of_case_party_id` /
   `required_of_case_property_id`. "Applicant — PAN Card" and "Co-applicant —
   PAN Card" are two visibly different rows, from association data, not from
   string concatenation in the frontend.

6. ADDITIONAL DOCUMENTS. `POST /api/cases/:id/requirements` (case.update)
   adds one hand-picked requirement to one case, from the CONTROLLED document
   type catalogue — never free text. Required and Additional are separate
   sections. Regeneration passes custom rows through untouched. In a
   submission they are candidates like any other, carrying `isCustom` so the
   Banks tab can say which are this case's own; package contents remain
   exactly what the operator ticked, so nothing is auto-attached.

7. SESSION LIFECYCLE. An inactivity timeout (AOS_SESSION_IDLE_MS, default 2h)
   alongside the existing absolute lifetime (AOS_SESSION_TTL_MS, 12h), both
   checked server-side on every request; a lapsed session is REVOKED, on its
   own connection so the 401's transaction rollback cannot discard it. The
   browser token moved from localStorage to sessionStorage, so closing the
   browser ends the session there too — a convenience, not the control.
   Deactivation and password reset already revoked sessions and still do.
   No beforeunload/unload anywhere.
