PHASE 1 — COLUMN MASKING / ADR-026
STATUS: COMPLETE (4d56eed)
PRIORITY: BLOCKER
------------------------------------------------------------

Goal:
Protect sensitive customer information so ordinary employees cannot
retrieve full sensitive values merely because they have normal
person.read access.

Scope:
  - PAN / identifiers
  - Bank account information
  - Date of birth
  - Address / pincode where covered by the final ADR-026 design
  - Other sensitive columns explicitly identified by ADR-026

Requirements:
  - Use the existing permission architecture.
  - Do not invent a second permission system.
  - Normal roles receive appropriately masked values.
  - Explicit permission is required for full-value reveal.
  - Full-value reveal is server-side authorized.
  - Full-value reveal is audited.
  - Do not leak raw values through alternate endpoints.
  - Preserve RLS as row visibility, not business authorization.

Existing tables.ts maskedColumns declarations include:
  - person_identifier.value_raw
  - referrer_profile.commission_terms
  - submission.login_fee_amount

DOB/address/pincode need deliberate treatment in the domain model.
Do not assume masking semantics without reviewing ADR-026.

Exit criteria:
  - Security tests pass.
  - No sensitive-field endpoint leaks raw values.
  - Authorized reveal works and is audited.
  - Unauthorized reveal is denied.
  - Existing workflows remain functional.

PHASE 2 — ADMIN-SCREEN HONESTY
STATUS: COMPLETE (342e649)
PRIORITY: BLOCKER-CLASS UX / DATA-INTEGRITY TRAP
------------------------------------------------------------

Resolution: Products (LendingProducts.tsx), the Lender Catalogue
(LenderCatalogue.tsx, all six panels), and the 14 "simple" Master Data
vocabulary sections (MasterData.tsx) had every Add/Edit/Deactivate
control removed — they are now read-only reference browsing over the
per-browser prototype dataset. Document Types, Rejection Reasons,
Document Requirement Rules and Thresholds were already
PostgreSQL-authoritative (commit c91fc70) and were left untouched,
keeping their real edit controls. NotConnectedBanner was reworded to
state plainly that the data is a read-only, per-browser preview, not
production configuration. Nav gating (App.tsx) was already correct —
the four admin nav links are gated on master_data.manage, not
master_data.read — so no permission-model change was required.
No new CRUD, no new backend routes, no schema changes.

Goal:
Ensure the UI does not pretend that disconnected localStorage
configuration is authoritative.

Current problem:
  - Products screen
  - Lender Catalogue
  - Most remaining Master Data sections

Some screens still write to browser localStorage while the real
operational system uses PostgreSQL. An employee could believe they
changed production configuration when the backend ignores the change.

Scope:
  - Remove or clearly label disconnected/local-only functionality.
  - Do not build unnecessary CRUD just to make every screen live.
  - Preserve Item 4's PostgreSQL-authoritative configuration.
  - Products/Lenders remain read-only unless a later business decision
    explicitly changes that scope.

Exit criteria:
  - No screen falsely presents localStorage data as authoritative.
  - Users cannot mistake local changes for office-wide changes.
  - Production configuration has one clear source of truth.
  - No unnecessary CRUD expansion.

PHASE 3 — CONCURRENCY & AUDIT HARDENING
STATUS: COMPLETE
PRIORITY: HIGH / PRODUCTION SAFETY
------------------------------------------------------------

Goal:
Make multi-user, multi-PC operation safe.

Known issues (confirmed in the code, not just the roadmap):
  - `sendPackage` (Backend/submissions.ts) never checked whether an
    identical send was already under way or already complete before
    creating a new `submission_package` and dispatching email. Two
    near-simultaneous calls (two employees, or one double-click) could
    both pass the document-set fingerprint check and both reach
    `provider.send` for the same documents before either transaction's
    writes were visible to the other. The existing
    `where status = 'not_submitted'` guard on `submission.status`
    prevented a second CASE transition, but not a second DISPATCH — the
    email had already gone to the bank by the time that guard ran.
  - `regenerateRequirements` (Backend/requirements.ts) ran on every read
    of a case's requirements (`listCaseRequirements`, called from a GET),
    inserting/updating/retiring `document_requirement` rows with no
    audit event at all — and even its own UPDATE was unconditional,
    rewriting a row to the values it already had on every call.

Resolution:
  - Backend/submissions.ts: `sendPackage` and `retryPackage` now open
    their critical section with `pg_advisory_xact_lock(hashtextextended
    (submissionId, 0))` — transaction-scoped, released automatically on
    commit/rollback, keyed on the submission id so different submissions
    (including two submissions on the same case) never block each other.
    After the lock is held, `sendPackage` re-reads authoritative state
    and checks for an already-`sent` package whose document set
    (id@version) matches the one being sent; if one exists, it returns
    that package's result instead of creating a duplicate and calling
    the provider again. A different document set (a document added,
    replaced or removed) is a genuinely new batch and is not blocked —
    preserving the existing "a second send is a new package" behavior
    for a deliberate resend. A failed/partially-sent package is
    untouched by this check, so `retryPackage` continues to work
    exactly as before, now itself serialized by the same lock.
  - Backend/requirements.ts: `regenerateRequirements` now compares each
    row's would-be new values against what is already on file before
    writing, and only executes the UPDATE when something actually
    differs. Every insert, real update and retirement (mark
    `not_applicable`) is tallied; if the tally is non-zero, one batched
    `requirement.regenerated` event is recorded (Backend/events.ts,
    `recordSystemRequirementEvent`) in the SAME transaction as the
    mutations, as a `system`-actor event (nobody clicked "regenerate";
    the reconciliation is a side effect of reading the case, the same
    reasoning `case.stage_changed` already uses for the transition
    machine's own automatic moves). A reconciliation that changes
    nothing writes no event. The payload carries only counts and
    requirement ids — no names, no document type labels, no case-party
    linkage.
  - No database migration. `pg_advisory_xact_lock` needs no schema
    change; the audit event reuses the existing `event` table (its
    `entity_type` column is unconstrained text) and the existing
    `recordSystem*Event` pattern.
  - `listCaseRequirements` remains a GET that regenerates on read — this
    was deliberately NOT changed to a separate mutation endpoint. The
    existing architecture (Backend/cases.ts's stage-transition guard,
    the All Cases progress list) depends on regeneration running inline
    on every read, and BR-050 ("a state change and its event commit
    together, or the change does not happen") is satisfied by the fix
    above without moving where regeneration happens. Splitting read from
    write here would be the broad REST redesign this phase is explicitly
    scoped to avoid.

Scope:
  - Make submission idempotent / transactionally safe. DONE.
  - Prevent duplicate lender emails. DONE.
  - Handle concurrent submissions correctly. DONE.
  - Move mutating regeneration behavior behind the appropriate mutation
    path if required by the existing architecture. NOT REQUIRED — see
    resolution above; the existing inline-on-read architecture is kept.
  - Add the missing audit event. DONE.
  - Preserve existing append-only audit semantics. DONE — the `event`
    table's append-only trigger and payload discipline are untouched.

Exit criteria:
  - Concurrent submission cannot send duplicate packages. PROVEN —
    Backend/submissions.test.ts, "concurrency — sendPackage serialises
    on the submission (Phase 3)".
  - Repeated submission is safely handled. PROVEN — same suite, plus the
    pre-existing retry regression tests (unmodified, still passing).
  - Mutating operations are represented correctly in the API. Requirement
    regeneration's mutation is now audited; see above for why the GET
    shape itself was kept.
  - Required audit events exist. PROVEN — Backend/requirements.test.ts.
  - Concurrency tests pass. PROVEN — full integration suite: 159/159.

PHASE 4 — CASE COMPLETENESS
STATUS: NOT STARTED
PRIORITY: HIGH / REQUIRED FOR BROADER REAL-WORLD CASES
------------------------------------------------------------

Goal:
Represent the parties and assets that real loan cases actually contain.

Known gap:
  - No route/workflow currently exists to add:
      * co-applicant
      * guarantor
      * property
  - Requirement checklists can therefore be incomplete for common
    secured or multi-party loan cases.
  - Requirement waiving is also not implemented.

Scope:
  - Add/manage co-applicants.
  - Add/manage guarantors.
  - Add/manage properties where required.
  - Ensure requirement rules consume the correct parties and properties.
  - Implement controlled requirement waiving if required by the existing
    business model.
  - Preserve auditability and authorization.

Exit criteria:
  - Real multi-party cases can be represented.
  - Secured-property cases can be represented.
  - Requirement generation reflects those relationships.
  - Waiving is controlled and audited if implemented.

This phase must not become a general redesign of the case system.

============================================================

After the development phases, there is a separate OFFICE SERVER
CUTOVER GATE. This is not another coding phase.

The office server must then be configured and verified:

  1. Take a verified production backup.
  2. Apply all required migrations.
  3. Configure aos_app with a strong production password.
  4. Keep administrative DB credentials separate.
  5. Configure the production .env.
  6. Run bootstrap-production.
  7. Confirm the five development accounts are inactive.
  8. Configure LAN binding / production web server.
  9. Configure Windows service startup.
  10. Configure scheduled backup.
  11. Configure firewall rules.
  12. Verify from a second office PC.
  13. Reboot the server and verify automatic recovery.
  14. Configure production Gmail credentials.
  15. Verify login and permissions.
  16. Verify existing case visibility.
  17. Verify document upload/download/verification.
  18. Verify lender submission safely.
  19. Verify backup and restore on the real hardware.
  20. Confirm designated server and backup/storage topology.
  21. Resolve orphaned document files only through an explicit,
      reviewed cleanup procedure; never blindly delete them.

The office database must NEVER be replaced with the disposable
Home-PC database.

============================================================
WHAT "PRODUCTION READY" MEANS
============================================================

AOS is production-ready for the INITIAL production scope when:

  - Authentication and authorization are secure.
  - Sensitive customer information is appropriately protected.
  - PostgreSQL is the authoritative operational database.
  - Document storage is durable and backed up.
  - Restore has been proven.
  - Concurrent submission cannot duplicate lender sends.
  - Audit trail is reliable and append-only.
  - Configuration screens cannot falsely imply local changes are
    production changes.
  - Real customer cases can be represented accurately enough for
    the initial business workflow.
  - The production server survives restart/reboot.
  - Employees can use the system from another office PC.
  - Backup runs automatically and has been verified.
  - Production credentials are configured securely.
  - Initial workflow works end-to-end:
      customer → case → requirements → documents →
      verification → bank submission
  - No known BLOCKER remains.

IMPORTANT:
Production-ready does NOT mean every planned AOS feature is complete.

Not prerequisites for first production cutover unless the business
changes scope:
  - Full Products CRUD
  - Full Lenders CRUD
  - Management dashboards
  - OCR/AI
  - WhatsApp enhancements
  - Advanced analytics
  - Future workflow polish
  - Every possible post-submission outcome feature

============================================================
ANTI-SCOPE-CREEP RULE
============================================================

Before starting any new task, ask:

"Does this directly satisfy a remaining production phase, its exit
criteria, or the office cutover gate?"

If NO:
  Do not implement it during Production Readiness.
  Record it as a later enhancement instead.

Do not invent new Stage 4 items.
Do not renumber phases because a new issue is discovered.
If a newly discovered issue is a genuine production blocker, attach
it to the closest existing phase or explicitly flag it for roadmap
review before implementation.

The goal is not to make AOS perfect.

The goal is to make the defined initial production workflow safe,
reliable, secure, recoverable and usable with real client data.
